Where each version spends its time

Eager: HBM bandwidth and N² memory

Only the two matmuls do real math. The six elementwise and reduction kernels in between each stream a full B·N² tensor through HBM, which adds up to 7 reads and 5 writes of N² per forward. d_model barely matters (+15% from 16 to 128). Four N² tensors are live at the peak, so N = 16 384 (8 GiB each) runs out of memory.

torch.compile: same algorithm, fewer passes

Inductor fuses scale and softmax into one or two Triton kernels, cutting N² traffic to roughly 2 reads and 2 writes. That gives about 2× on forward. Two N² tensors are still saved for backward, so memory still grows as N², and backward still runs out of memory at 16 384.

Flash (PyTorch): memory fixed

Only Q, K, V, O and L are stored, which is O(B·N·d): 88 MiB vs 4.1 GiB at d = 64, N = 8192. The online softmax rescales old partial sums by α = exp(m_old − m_new), so the result is exact (see the toy check below the code).

Flash (PyTorch): launch-bound, ~10× slower

There are (N/B)² tile pairs, each about 14 tiny kernels launched from a Python loop. At N = 16 384 with 128-tiles that is 16 384 pairs at ~0.16 ms each, about 11 µs per launch, with the GPU mostly idle. The tiles still go through HBM or L2 between kernels. The Triton kernel (4.2.2 b) fuses the whole inner loop so the tiles stay on-chip.
